# ETA model

Predicts **minutes remaining until delivery** (P50 and P90) and re-predicts on every order state
change (created → picking → rider assigned → out for delivery). Published as `eta.updated` events.

**Read this first: every accuracy number here is measured on simulated trips.** The simulator's
physics (rush-hour traffic, rain, slow H3 cells, picker queues) live in
`packages/common/src/darkstore_common/world.py` and I designed the effects, so a model that learns
them is not evidence of real-world accuracy. What the numbers do show: the pipeline is correct end
to end, the model recovers effects that exist in the data, it does not leak the future, and its
intervals are calibrated.

## Pipeline

| Step | Where |
|---|---|
| Trip generator → Parquet (4 snapshots per order, only what is knowable at that moment) | `services/eta/.../simulate.py` |
| Features: distance, hour (cyclic), day-of-week, rain, active orders in store, picker queue depth, idle riders near, rider-to-store distance, H3 cell slowness | `features.py` |
| Train P50 + P90 LightGBM quantile regressors in scikit-learn pipelines, chronological split, early stopping | `train.py` |
| P90 calibrated with a split-conformal offset fitted on the validation set | `train.py` |
| In-process serving, feature flag, heuristic fallback, hot reload | `predictor.py` |
| Event-driven service (`eta.updated`, predicted-vs-actual `eta.outcomes`) | `service.py` |
| Retrain on fresh trips, promote only if better on the same holdout | `retrain.py` |

Commands: `make train` (generate, train, log to MLflow, write `docs/ml/eta-report.md`) and
`make retrain` (promotes into `models/eta/current` only if it beats the live model; running
services pick it up within `ETA_RELOAD_SECONDS`). MLflow UI: http://localhost:5001.

## Leakage controls
- Time-based split **by trip** (70/15/15): no trip straddles sets. Note the simulator has no drift
  over time, so this split is effectively i.i.d.; it guards against leakage, it does not test drift.
- H3 cell statistics are computed from training rows only, and training rows use *out-of-fold*
  stats (never partly their own target).
- Snapshot features contain only what exists at that stage (pick time is NaN until picking ends;
  the real rider's distance is only known after assignment; before that it is an estimate).

## Baselines
- **Heuristic** (also the production fallback): distance ÷ 20 km/h × 1.4, flat 3 min pick, P90 = ×1.35.
- **Calibrated heuristic**: the same formula with two scale factors fitted on the training period per
  (stage, raining, rush-hour band). This is the fair comparison: the naive heuristic is biased (it
  assumes 20 km/h in a city that averages slower), so beating it alone flatters the model. An earlier
  version of this baseline had no rain/rush terms and made the model look 53% better; the stronger
  baseline gives the honest **-15% MAE (95% CI 14-17%)** at equal ~90% coverage with ~21% narrower
  intervals.

Latest numbers: see [eta-report.md](eta-report.md) (regenerated by every `make train`).

## Serving behavior
`predict()` never raises. It returns the heuristic (and counts the reason in `fallbacks`) when the
flag `ETA_MODEL_ENABLED` is off, the model is missing/corrupt, inputs are invalid or out of range,
the model throws, or the output is non-finite.

## Live accuracy (measured on the running stack, not offline)
First prediction at order time vs actual delivery, 123 delivered orders, low sustainable load
(`SIM_ORDERS_PER_MINUTE=0.5`, start hour 15), same orders scored three ways:

| | MAE (sim-min) | Bias | MAPE | P90 coverage |
|---|---|---|---|---|
| LightGBM (served model) | 6.64 | -4.15 | 13.4% | 74.8% |
| Naive heuristic | 22.03 | -22.03 | 46.8% | 8.1% |

Remaining gap to the offline numbers (3.98 MAE, 90% coverage): the live fleet drifts away from the
stores (riders stay where they delivered), so rider wait and pickup rides are longer and more
variable than the generator's; the model under-predicts by ~4 min and its P90 is too tight. The
drift dashboard (P5) will track exactly this from `eta.outcomes`.

How the first live measurement was wrong, for the record: it showed MAE 12.8, and investigating it
found (1) training/serving feature skew (customer distribution, pick-time queues, queue-depth and
hour definitions) which is now fixed, and (2) a real simulator bug: rider-sim moved riders by a
*nominal* 0.2 s per step although a step over 120 riders took longer, so riders ran slower than the
simulated clock. It now uses measured elapsed time. At the default dinner-rush rate the 120-rider
fleet saturates (orders queue for riders), which is the capacity limit the P6 load tests will report.

## Known gaps / what real data would change
- Live riders have no handover time and no weather feed (rain comes from the same simulated calendar).
- Cell speed: the generator uses the store cell for the pickup leg and the customer cell for the
  delivery leg; the live rider-sim uses the rider's current cell as it moves.
- Real traffic feeds, per-rider history, and a feature store would replace the generator and the
  Redis fleet lookup.
- Model bundles are joblib pickles: load only from directories you control (the compose mount is
  read-only).
